1. Overview

This page is the permanent Source of Truth for all architecture, migration, and development protocol decisions in the KriolosPOS project — a modernized fork of uniCenta oPOS.

It governs the incremental extraction of business logic from a legacy Java Swing monolith into a clean, modular, framework-agnostic domain layer using Java 17 and Hexagonal Architecture principles.

All 14 rules defined here are mandatory and non-negotiable. Any contribution that violates a rule must be rejected at review time.

2. Rule 1 — Core Philosophy: KISS Principle

"SIMPLE IS ALWAYS THE BETTER CHOICE."

2.1. Guidelines

  • Avoid introducing complex Design Patterns unless the business logic forces it.

  • Prefer readable, explicit, linear code over deeply nested abstractions.

  • Do not create interfaces, factories, or registries speculatively (YAGNI).

  • Get straight to the code — no architectural manifestos in commit outputs.

2.2. Java 17 Toolbox

Use modern Java 17 features to write concise, bulletproof domain logic with minimal boilerplate:

Feature Use Case

record

Immutable domain models, value objects, command/result payloads

Sealed interfaces

Exhaustive domain state machines (e.g., PaymentState, TicketStatus)

Pattern matching (instanceof)

Type-safe dispatch without casting boilerplate

Switch expressions

Exhaustive, expression-form business rule mapping

Optional<T>

Explicit absence without null propagation

List.of() / Map.of()

Immutable data structures for domain results
Example — Sealed domain result
public sealed interface PaymentResult
    permits PaymentResult.Success, PaymentResult.Declined, PaymentResult.Error {

    record Success(BigDecimal amountPaid, BigDecimal change) implements PaymentResult {}
    record Declined(String reason)                          implements PaymentResult {}
    record Error(String technicalMessage)                  implements PaymentResult {}
}

3. Rule 2 — Strangler Fig Pattern

  • The existing Swing UI is the active, production-ready delivery mechanism and must remain fully compilable and functional at all times.

  • New domain logic grows alongside legacy code — never instead of it.

  • Legacy code is strangled incrementally: one feature, one file, one method at a time.

A contribution that breaks Swing compilation is an immediate blocker regardless of the quality of the domain layer change.

4. Rule 3 — Hexagonal Architecture (Ports & Adapters)

 +--------------------------------------------------------+
 |  DRIVING ADAPTERS (Inbound)                            |
 |  Swing JPanel/ActionListener  |  REST (future)         |
 +-------------------+------------------------------------+
                     | calls
 +-------------------v------------------------------------+
 |  DOMAIN CORE                                           |
 |  Domain Services  |  Domain Records  |  Domain Events  |
 +-------------------+------------------------------------+
                     | calls
 +-------------------v------------------------------------+
 |  DRIVEN ADAPTERS (Outbound) - implement Ports          |
 |  DataLogicSales  |  JasperReports  |  BeanShell        |
 |  Printer         |  Peripheral     |  FileSystem        |
 +--------------------------------------------------------+

  • Inbound Port: A use-case interface the driving adapter calls (optional for simple cases).

  • Outbound Port: An interface the domain core calls; infrastructure implements it.

  • Domain core has zero knowledge of Swing, JDBC, JasperReports, or BeanShell.

4.1. Swing Adapter Responsibility Contract

A refactored Swing Adapter method does only three things:

  1. Extract raw values from visual components (getText, getSelectedItem, etc.)

  2. Delegate to the Domain Service with a typed command/request object

  3. Apply the domain result back to visual components (setText, setEnabled, etc.)

Adapter method skeleton
private void onConfirmPaymentAction() {
    // 1. Extract
    BigDecimal cashReceived = new BigDecimal(txtCashReceived.getText().trim());

    // 2. Delegate
    PaymentResult result = paymentService.processPayment(
        PaymentCommand.of(sessionContext, activeTicket, cashReceived)
    );

    // 3. Apply
    switch (result) {
        case PaymentResult.Success s -> {
            lblChange.setText(s.change().toPlainString());
            closePaymentPanel();
        }
        case PaymentResult.Declined d -> showError(d.reason());
        case PaymentResult.Error e   -> logAndAlert(e.technicalMessage());
    }
}

5. Rule 4 — Modular Monolith: Bounded Contexts

Each business capability lives in a strictly isolated domain module/package:

com.openbravo.pos.domain.shared        <- Shared Kernel only
com.openbravo.pos.domain.sales
com.openbravo.pos.domain.inventory
com.openbravo.pos.domain.payments
com.openbravo.pos.domain.rbac
com.openbravo.pos.domain.navigation
com.openbravo.pos.domain.reporting

5.1. Cross-Module Communication Rules

  • A module cannot import internal classes of another module.

  • Cross-module communication uses only:

    • Shared Kernel value objects (com.openbravo.pos.domain.shared)

    • Public API interfaces (outbound ports exposed by the producing module)

    • Domain Events (immutable records published at module boundaries)

  • Each module must be copy-paste portable into a standalone Quarkus, Spring Boot, or WebforJ project with no hidden sibling-module dependencies.

6. Rule 5 — Package Namespace Preservation

The historical base namespace com.openbravo is frozen and immutable.

Constraint Detail

New domain packages

Created under com.openbravo.pos.domain.*

Existing legacy classes

Never renamed or moved

Legacy integration

Only via Outbound Port interfaces; legacy classes implement or wrap ports

7. Rule 6 — Mandatory Invariants

7.1. 6.1 Data Integrity — SQL Preservation

  • Existing SQL queries, result-set mappings, and DB schema interactions are never modified during a domain extraction.

  • Extraction wraps legacy DataLogic* singletons behind an Outbound Port; the SQL inside remains byte-for-byte identical.

7.2. 6.2 Financial Precision — BigDecimal

  • Never use float or double for monetary values.

  • Preserve the exact RoundingMode and BigDecimal scale already present in legacy code.

  • Domain records carry monetary amounts as BigDecimal.

Shared Kernel Money value object
// com.openbravo.pos.domain.shared
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        amount = amount.setScale(2, RoundingMode.HALF_EVEN); // match legacy scale
    }
}

7.3. 6.3 Multi-Tax System Integrity

  • Complex, nested, or cumulative multi-tax logic must remain structurally intact when separated from UI context.

  • Tax rules are modelled in the domain layer — not flattened or simplified during extraction.

7.4. 6.4 Internationalization (I18N / L10N)

  • Domain services return locale-agnostic data payloads (codes, enums, BigDecimal, identifiers).

  • The Swing Adapter resolves resource bundle strings for display.

  • No user-facing strings are hardcoded in the domain layer.

8. Rule 7 — UI Adapter & NetBeans Form Rules

8.1. 7.1 NetBeans XML GUI Form Preservation

Never manually edit code inside // GEN-BEGIN:initComponents …​ // GEN-END:initComponents blocks. These blocks are owned by the NetBeans GUI Builder and will be overwritten.
Wiring pattern
public MyPanel() {
    initComponents();       // GEN-BEGIN/END - do not touch
    initDomainAdapters();   // our hook - all domain wiring goes here
}

private void initDomainAdapters() {
    // setName() calls, listener wiring, service injection
}

8.2. 7.2 Component Identification — setName() URN Anchoring

Every Swing component touched during a refactoring must receive a unique identifier via .setName() following the URN specification with mandatory kriolos: prefix: kriolos:<domain>:<component-or-action>.

Rule Format Example

URN specification

kriolos:<domain>:<component>

btnNavBack.setName("kriolos:navigation:back")

Action / Button URN

kriolos:<domain>:<action>

btnNavForward.setName("kriolos:navigation:forward")

Field / Input URN

kriolos:<domain>:<field>

txtCashReceived.setName("kriolos:sales:cash-received-amount")

Applied in initDomainAdapters()

Never in GEN blocks

btnConfirm.setName("kriolos:sales:confirm-payment")

Purpose

Automation hook & web-layer mapping

Standardized URN links Swing to Domain to future Web component

9. Rule 8 — Quality, Testing & Automation

9.1. 8.1 JUnit 5 — Domain Service Tests

Every extracted Domain Service or Record must have a corresponding JUnit 5 test class covering:

  • Happy path

  • Edge cases (zero amounts, max values, boundary tax transitions)

  • Rounding correctness (assert BigDecimal scale and value exactly)

  • Null / invalid input guards

Test naming convention
src/test/java/com/openbravo/pos/domain/sales/PaymentServiceTest.java
Minimal test skeleton
@DisplayName("PaymentService")
class PaymentServiceTest {

    @Test
    @DisplayName("exact change is zero when cash equals total")
    void exactPayment_yieldsZeroChange() {
        var result = paymentService.processPayment(
            PaymentCommand.of(session, ticket, new BigDecimal("12.50")));
        assertInstanceOf(PaymentResult.Success.class, result);
        assertEquals(BigDecimal.ZERO.setScale(2),
            ((PaymentResult.Success) result).change());
    }
}

9.2. 8.2 Automation Module Integration

  • setName() (Rule 7.2) is the primary automation hook — no additional instrumentation required.

  • Provide a boilerplate automation integration test per adapter:

@AutomationTest(screen = "PaymentPanel")
class PaymentPanelAutomationTest {

    @Test
    void workflow_cashPayment_capturesScreenshot() {
        automation.navigate("PaymentPanel");
        automation.type("cashReceivedAmount", "20.00");
        automation.click("confirmPayment");
        automation.assertVisible("changeAmount");
        automation.screenshot("cash_payment_success");
    }
}

10. Rule 9 — Specification Assets (Antora Canonical Paths)

Every refactoring task must produce or update assets at:

Asset Type Canonical Path

Behavioral flow / business rules (AsciiDoc)

modules/<module>/pages/specification/<feature>.adoc

Data contract / payload schema (JSON Schema)

modules/<module>/assets/attachments/specification/<feature>.schema.json

11. Rule 10 — Stateless Domain (No Legacy Singletons)

  • The domain layer must be completely stateless and thread-safe.

  • Domain services must never access static global objects such as AppView, JRootApp, or any Swing singleton.

  • Active user context, terminal ID, locale, and session state are passed as immutable parameters into every domain use case call.

SessionContext — Shared Kernel record
// com.openbravo.pos.domain.shared
public record SessionContext(String operatorId, String terminalId, Locale locale) {}
Anti-pattern (forbidden)
// FORBIDDEN - couples domain to Swing singleton
String operatorId = AppView.getApp().getSession().getCurrentUser().getId();
Correct pattern
// CORRECT - Swing Adapter extracts and passes context explicitly
PaymentResult result = paymentService.processPayment(
    PaymentCommand.of(sessionContext, activeTicket, cashReceived)
);

12. Rule 11 — Domain Exceptions Only

  • Business logic must never throw or propagate infrastructure-specific exceptions (SQLException, JRException, IOException) across layer boundaries.

  • All error conditions wrap into semantic, domain-scoped exceptions within the bounded context package:

com.openbravo.pos.domain.sales.SalesException
com.openbravo.pos.domain.payments.PaymentException
com.openbravo.pos.domain.inventory.InventoryException

  • The infrastructure adapter catches raw infrastructure exceptions and rethrows as the domain exception.

  • The Swing Adapter catches the domain exception and renders the error. The domain never calls UI message loops.

Exception wrapping in infrastructure adapter
@Override
public TicketRecord findById(String ticketId) {
    try {
        // ... JDBC call, SQL unchanged ...
    } catch (SQLException e) {
        throw new SalesException("Ticket lookup failed: " + ticketId, e);
    }
}

13. Rule 12 — Full Data Hydration

  • Persistence Outbound Ports must return fully materialized records — all fields populated before the method returns.

  • Forbidden across layer boundaries:

    • Active ResultSet or JDBC cursor references

    • Lazy-loaded proxy objects

    • Unclosed streams or iterators backed by a live DB connection

  • Domain record types are the canonical hydrated form; construct them inside the infrastructure adapter.

Infrastructure adapter hydration pattern
@Override
public List<TicketLineRecord> findLinesByTicket(String ticketId) {
    List<TicketLineRecord> lines = new ArrayList<>();
    try (PreparedStatement ps = conn.prepareStatement(SQL_FIND_LINES)) {
        ps.setString(1, ticketId);
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                lines.add(new TicketLineRecord(
                    rs.getString("ID"),
                    rs.getString("PRODUCT"),
                    rs.getBigDecimal("PRICE"),
                    rs.getInt("UNITS")
                ));
            }
        }
    } catch (SQLException e) {
        throw new SalesException("Line fetch failed: " + ticketId, e);
    }
    return List.copyOf(lines); // immutable - safe across threads
}

15. Rule 14 — SDLC & Git Branching Protocol

15.1. 14.1 Git Branching Mandate

Every incremental feature extraction or refactoring task runs on a dedicated feature branch:

git checkout -b feature/decouple-<module-name>
# e.g.: feature/decouple-navigation, feature/decouple-sales-tax

  • All file creations, code diffs, and spec assets are committed to this branch.

  • Branch is never merged until Phase E verification is complete.

15.2. 14.2 Agile SDLC Framework — Mandatory Iterative Phases (Java Swing Specialized)

Modern desktop applications combining rich Java Swing presentation with Hexagonal Domain Architecture require an industry-standard Agile lifecycle. This lifecycle bridges Agile/Scrum single-piece flow and Test-Driven Development (TDD) with desktop-specific constraints: Swing Event Dispatch Thread (EDT) safety, NetBeans GUI Builder preservation, headless CI/CD execution, and component testability via Rule 7.2 URN anchoring.

Every user story or refactoring increment must progress through these six mandatory phases:

Phase Stage Name Agile Deliverable Desktop & Swing Focus

1

Discovery & Story Refinement

User Story with Gherkin ACs + Definition of Done (DoD)

UI component & state audit, EDT latency assessment, modal dialog inventory

2

Architectural Contract & Port Design

Pure Java 17 Records/Ports + Rule 7.2 URN Schema

Zero GUI/SQL dependencies in domain, async callback contracts, busy-state specification

3

Test-First Harness & Automation Setup (TDD)

JUnit 5 Domain Tests + AssertJ-Swing Action Drivers

URN anchoring tests in ModalPanelUrnAnchoringTest, EDT isolation, System.exit protection

4

Component Implementation & Adapter Wiring

Swing Panel/Frame + initDomainAdapters()

NetBeans GEN blocks untouched, event delegation rule, non-blocking SwingWorker, progress indicators

5

Automated Verification & Visual Quality Gates

Green CI Matrix across JDK 17 to latest

Pure bytecode compilation (--release 17), Wayland/X11 non-black frame assertions, test automation suite

6

Agile Trunk Integration & Retrospective

Atomic PR + Conventional Commit

Single-piece flow (no stacked branches), Strangler Fig verification, known issues log

15.2.1. Phase 1: Discovery & Story Refinement (Backlog Grooming)

  • User Story Definition: Express business requirements with explicit Acceptance Criteria using Gherkin syntax (Given-When-Then).

  • Swing Component & State Audit:

    • Identify all touched Swing containers (WindowShell, ApplicationShell, WordspacePanel, AuthenticationPanel, or dialogs).

    • Map UI dependencies and couplings to legacy singletons (AppView, AppUserView, DataLogicSystem).

  • EDT & Latency Risk Assessment:

    • Classify every operation: Fast/In-Memory (safe on EDT) vs I/O / Database / Network / Hardware (strictly forbidden on EDT).

  • Modal Dialog Strategy:

    • Identify any legacy blocking JDialog or JOptionPane calls.

    • Plan replacement with non-blocking panel-based overlays (PosUIModal / InFrameOverlayModalStrategy) to prevent EDT deadlocks and enable headless automation.

15.2.2. Phase 2: Architectural Contract & Ports/Adapters Design

  • Pure Domain Model:

    • Formulate domain records, value objects, and domain services in kriolos-opos-domain using Java 17 constructs.

    • Strict Boundary Constraint: Domain classes must have zero imports from javax.swing., java.awt., com.openbravo.pos.forms., or java.sql..

  • Port Interfaces & Callbacks:

    • Define Driving Ports (invoked by Swing UI) and Driven Ports (implemented by infrastructure).

    • Define asynchronous callbacks (e.g. DatabaseActivationCallback) for multi-step or long-running workflows.

  • Rule 7.2 URN Anchoring Schema:

    • Draft the component identification mapping table following kriolos:<domain>:<component-or-action> (e.g. kriolos:auth:combo-databases, kriolos:auth:btn-select-database).

  • Asynchronous Busy State Specification:

    • Define visual state transitions for UI components: disable triggers, display indeterminate JProgressBar, update status text during background processing.

15.2.3. Phase 3: Test-First Harness & Automation Driver Construction (TDD / ATDD)

  • Domain Unit Tests First:

    • Create JUnit 5 unit tests verifying happy paths, error boundaries, and BigDecimal rounding scales.

  • URN Anchoring Verification:

    • Add test cases to ModalPanelUrnAnchoringTest verifying all interactive components expose their Rule 7.2 URNs via .getName() before wiring business logic.

  • Automation Driver / Action Facade:

    • Build or enhance reusable action drivers in kriolos-opos-automation/actions/ (e.g. DatabaseSelectionAction, LoginAction, MainWindowAction) utilizing AssertJ-Swing.

  • Test Isolation & Headless Safeguards:

    • Set machine.uniqueinstance=false to prevent singleton port collisions with dev environments.

    • Wrap application startup with StartPOS.setExitAction(Runnable) to prevent System.exit() from terminating the test JVM.

    • Ensure compatibility with virtual display framebuffers (xvfb) and in-memory 2D double buffering.

15.2.4. Phase 4: Component Implementation & GUI Builder Integrity (Swing Development)

  • NetBeans Protected Block Rule (Strict):

    • NEVER edit code inside // GEN-BEGIN:initComponents or // GEN-END:initComponents manually.

    • Structural layout changes belong in the NetBeans visual designer (.form file).

  • Generated Event Handler Delegation Rule:

    • Code inside // GEN-FIRST:event_…​ generated handlers MUST ALWAYS delegate immediately to a single private method (e.g. btnActivateActionPerformed delegates to activateSelectedDatabase()).

    • Document all extracted methods with comprehensive Javadoc detailing purpose, thread safety, and UI state transitions.

  • Domain Adapter Wiring (initDomainAdapters() / initPanel()):

    • Register Rule 7.2 .setName(…​) URN anchors programmatically outside GEN blocks.

    • Attach domain listeners and wire presenters.

  • EDT Concurrency & Asynchronous Execution:

    • All database, filesystem, network, or hardware operations must execute off the EDT using SwingWorker<T, V> or asynchronous background workers.

    • UI state mutations must always be dispatched back to the EDT via SwingUtilities.invokeLater() or SwingWorker.done().

  • Real-Time Asynchronous User Feedback:

    • Whenever a background operation is initiated, immediately set the UI into a responsive busy state (e.g. show kriolos:auth:progress-bar, display status message, disable duplicate action buttons).

15.2.5. Phase 5: Automated Verification & Visual Quality Gates (CI/CD Matrix)

  • JDK 17 Baseline Verification:

    • Validate that all code compiles strictly with Java 17 bytecode targets (<maven.compiler.release>17</maven.compiler.release>). Never utilize post-17 APIs (e.g. SequencedCollection).

  • Continuous Multi-Tier Verification:

    1. mvn test -pl kriolos-opos-domain (Unit tests 100% green).

    2. mvn test-compile -pl kriolos-opos-app (Swing application clean build).

    3. mvn clean test-compile -f kriolos-opos-automation/pom.xml (Automation test compilation).

    4. mvn test -f kriolos-opos-automation/pom.xml -Dtest=ModalPanelUrnAnchoringTest (URN verification green).

  • Framebuffer & Visual Rendering Assertion:

    • Autonomous robot tests take visual snapshots and assert non-black dialog/panel rendering (>50% non-black pixels) on Linux/Wayland graphics environments.

15.2.6. Phase 6: Agile Trunk-Based Integration, Atomic PR & Retrospective

  • Single-Piece Flow (No Stacked Branches):

    • Commit all changes to a dedicated feature branch (feature/<name>) cut from clean main.

    • Never stack a new feature on top of an unmerged feature branch.

  • Professional Conventional Commit:

    • Use standardized commit syntax: feat(…​), fix(…​), refactor(…​), test(…​), docs(…​).

    • Include structured bullet points detailing architectural rationale, component changes, and URNs.

  • Atomic Pull Request & Merge:

    • Submit Pull Request to main. Ensure all automated GitHub Actions CI matrix checks pass.

    • Squash and merge into main.

  • Clean Main Synchronization:

    • Run git checkout main && git pull origin main before starting the next feature branch.

  • Defect & Retrospective Tracking:

    • Record any platform-specific quirks (e.g. Wayland compositor rendering issues, X11 focus traps) in docs/modules/guide-devel/pages/troubleshooting-known-issues.adoc.

15.3. 14.3 Agile Trunk-Based Integration Protocol (Atomic PR & Merge)

CRITICAL CONSTRAINT: NEVER COMMIT OR PUSH DIRECTLY TO MAIN

Direct commits and direct pushes to main (or master) are strictly forbidden for both developers and AI assistants. All work—including small tweaks, documentation, and bug fixes—must be developed on a dedicated branch (feature/ or fix/) and merged into main exclusively through a reviewed Pull Request.

To maintain an Agile cadence with short, reliable feedback loops and eliminate dependency debt, the project strictly mandates an atomic PR-and-merge integration cycle:

feature/decouple-<module-A> (Phase A-E Complete)
  └── 1. Push branch to remote
  └── 2. Open Pull Request (PR) & Validate Automation Tests
  └── 3. Merge PR into main
        └── 4. Locally: git checkout main && git pull origin main
              └── 5. Cut next branch: git checkout -b feature/decouple-<module-B>

15.3.1. Mandatory Rules for Feature Transitions

  1. Never Commit or Push Directly to main (Strict): Always work on a dedicated branch. Ensure local main remains untouched except via git pull origin main.

  2. No Stacked Feature Branches (Strict): Never create a new feature branch (feature/decouple-<module-B>) off an unmerged feature branch (feature/decouple-<module-A>).

    • Rationale: Stacked branches drag unreviewed commits into future reviews, multiply merge conflict risks, blur bounded context boundaries, and pollute git diffs.

  3. Agile Single-Piece Flow: Each decoupled capability (e.g. navigation, sales, payments) represents a single, verifiable, production-ready increment. Merging it to main immediately anchors the Strangler Fig progress and provides a clean, green baseline for the next sprint or task.

  4. Continuous Verification Gate: A branch is ready for PR merge only when:

    • Code compiles strictly against minimum JDK 17 baseline (<maven.compiler.release>17</maven.compiler.release>) to satisfy the GitHub Actions CI/CD matrix (testing JDK 17 minimum up to the latest JDK).

    • Domain unit tests pass (mvn test -pl kriolos-opos-domain).

    • Swing app compiles without errors (mvn compile -pl kriolos-opos-app -am).

    • Robot automation test passes (mvn test-compile -f kriolos-opos-automation/pom.xml).

    • NetBeans GUI builder form blocks (// GEN-BEGIN) remain 100% untouched.

  5. Standard Transition Command Sequence:

    # 1. Push completed feature branch
git push -u origin feature/decouple-<current-module>

# 2. (After PR approved and merged on remote) Synchronize local main
git checkout main
git pull origin main

# 3. Cut next isolated feature branch from clean main
git checkout -b feature/decouple-<next-module>
