1. 1. Executive Summary & Architectural Vision

KriolOS POS is modernizing its application core by adopting Quarkus as its runtime and dependency injection backbone in a Desktop (Swing / FlatLaf) deployment topology.

Historically derived from OpenbravoPOS and Unicenta, the application traditionally relied on ad-hoc singleton registries (AppConfig, AppView.getBean()), manual JDBC connection management, legacy BeanShell scripting, Apache Velocity templating, and monolithic classpath loading.

Migrating to Quarkus Desktop provides:

  • Quarkiverse Quarkus Desktop (quarkus-desktop-swing): Modern AWT/Swing desktop lifecycle integration, CDI-driven windows, @RunOnEdt thread safety, native OS menu events, and automated GraalVM native image metadata.

  • Sub-Second Cold Boot: Build-time pre-indexing and class metadata resolution.

  • ArC (Build-Time CDI 4.0 Lite): Clean, typesafe dependency injection with compile-time verification, eliminating runtime reflection overhead.

  • Unified Modern Configuration: Full alignment with MicroProfile Config and SmallRye Config (established in PR #144).

  • Quarkus Qute Engine API: Ultra-fast, zero-reflection template engine replacing Apache Velocity for receipt and invoice printing.

  • QuickJS Embedded Script Engine: Modern, sandboxed ECMAScript (ES2020) engine replacing unmaintained BeanShell for business event rules.

  • Agroal High-Performance Connection Pooling: Robust connection lifecycle management across SQLite, MariaDB, MySQL, and PostgreSQL.

  • Seamless Cross-Platform Distribution: Packaging Quarkus fast-jar binaries with JPackage and custom JLink runtimes for native Linux (.deb, .rpm), Windows (.msi), and macOS (.dmg) installers.

Swing / EDT Guiding Principle: Quarkus manages the application lifecycle, CDI container, background worker pools, and persistence. The Graphical User Interface (Swing / FlatLaf) is initialized strictly within the Java AWT Event Dispatch Thread (EDT) via javax.swing.SwingUtilities.invokeLater() or through Quarkus Desktop’s @RunOnEdt / DesktopStartupEvent, cleanly separated from the Quarkus runtime bootstrap thread.

3. 3. Assets & Native Resources Specification (quarkus.native.resources.includes)

In traditional JVM execution, resource discovery relies on classpath crawling. In Quarkus desktop and native builds, all resources required at runtime must be deterministically declared at build time.

5. 5. ArC (Build-Time CDI Container) Architecture

5.1. 5.1 Service Decomposition

The business logic extracted from legacy Swing panels into kriolos-opos-domain will be registered as CDI beans:

package com.openbravo.pos.sales;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
public class SalesServiceImpl implements SalesService {

    @Inject
    InventoryService inventoryService;

    @Inject
    CustomerService customerService;

    @Override
    public TicketInfo createTicket() {
        return new TicketInfo();
    }
}

5.2. 5.2 Transition Pattern: The ArcBridge

During intermediate migration stages where legacy Swing classes still exist alongside modern CDI services, an ArcBridge provides typesafe access to CDI beans from Swing components without polluting UI classes with service locator antipatterns:

package com.openbravo.pos.cdi;

import io.quarkus.arc.Arc;

public final class ArcBridge {

    private ArcBridge() {}

    public static <T> T getBean(Class<T> beanClass) {
        return Arc.container().instance(beanClass).get();
    }
}

6. 6. Desktop UI Integration via Quarkiverse Quarkus Desktop (Swing)

6.1. 6.1 Overview & Dependency

The Swing desktop UI layer (kriolos-opos-app) will be integrated using Quarkus Desktop from the Quarkiverse community (https://github.com/quarkiverse/quarkus-desktop):

<dependency>
    <groupId>io.quarkiverse.desktop</groupId>
    <artifactId>quarkus-desktop-swing</artifactId>
    <version>1.0.0.Alpha1</version>
</dependency>

This extension provides: 1. Automated GraalVM Native Image Support: Configures reflection, resource bundles, JNI metadata, and copies required JDK native libraries (libawt.so, libfontmanager.so, awt.dll, libosxapp.dylib) automatically. 2. CDI-Powered Window Lifecycle: Turns standard JFrame and JPanel components into manageable CDI beans. 3. Thread Safety with @RunOnEdt and EdtExecutor: Eliminates manual SwingUtilities.invokeLater() boilerplate when returning from background worker threads. 4. Native OS Desktop Integration: Bridges macOS Application menu items (About, Preferences, Quit) directly into CDI events. 5. Live Coding in Dev Mode: Supports Quarkus Dev Mode live-reload for desktop Swing UI development.

6.2. 6.2 CDI Window Lifecycle

The main application window JRootApp becomes a managed @Singleton bean reacting to DesktopStartupEvent:

package com.openbravo.pos.forms;

import io.quarkiverse.desktop.awt.DesktopStartupEvent;
import jakarta.enterprise.event.Observes;
import jakarta.inject.Inject;
import jakarta.inject.Singleton;
import javax.swing.JFrame;

@Singleton
public class JRootApp extends JFrame {

    @Inject
    AppConfig config;

    @Inject
    SalesService salesService;

    void onStartup(@Observes DesktopStartupEvent event) {
        setTitle("KriolOS POS");
        setDefaultCloseOperation(JFrame.DO_NOTHING_ON_CLOSE);
        initUI();
        pack();
        setVisible(true);
    }
}

6.3. 6.3 Thread Safety: @RunOnEdt & EdtExecutor

Peripheral scanners, scales, and payment gateways operate asynchronously in background threads. quarkus-desktop-swing provides declarative dispatching back to the Swing Event Dispatch Thread:

package com.openbravo.pos.sales;

import io.quarkiverse.desktop.swing.RunOnEdt;
import io.quarkiverse.desktop.swing.EdtExecutor;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
public class SalesBarcodeScanCoordinator {

    @Inject
    EdtExecutor edtExecutor;

    @Inject
    TicketLineController ticketLineController;

    // Asynchronous background peripheral scan event
    public void onRawBarcodeReceived(String barcode) {
        // Runs in background worker pool
        ProductInfoExt product = lookupProductDatabase(barcode);

        // Dispatches safely to Swing EDT
        edtExecutor.execute(() -> {
            ticketLineController.addProductLine(product);
        });
    }

    // Alternatively, declarative annotation for automatic EDT execution
    @RunOnEdt
    public void updateCartUI(TicketInfo ticket) {
        // Guaranteed to run on Swing Event Dispatch Thread
    }
}

7. 7. Receipt Templating: Apache Velocity to Quarkus Qute (Engine API)

7.1. 7.1 Architectural Motivation

Currently, receipt, invoice, and customer display formatting is performed by Apache Velocity 2.x. While functional, Velocity presents significant limitations:

  1. Heavy Runtime Reflection: Velocity parses templates dynamically and inspects Java objects using reflection on every render pass.

  2. Cold Start Penalty: Velocity initializes introspectors and resource managers, slowing POS startup.

  3. GraalVM & Native Incompatibility: Dynamic introspection requires hundreds of explicit reflection registrations.

7.2. 7.2 The Quarkus Qute Standalone Engine API

Quarkus Qute provides a programmatic Engine API (io.quarkus.qute.Engine) that can be used standalone in desktop applications without requiring an HTTP server or REST endpoints:

import io.quarkus.qute.Engine;
import io.quarkus.qute.Template;

// Initialized as a singleton CDI bean or via SPI
Engine engine = Engine.builder()
    .addDefaults()
    .build();

// Parse and cache template
Template receiptTemplate = engine.parse(rawTemplateXml);

// Zero-reflection, sub-millisecond rendering
String renderedXml = receiptTemplate
    .data("ticket", ticket)
    .data("taxes", taxMap)
    .render();

7.3. 7.3 Implementation via ScriptEngineProvider SPI

Under kriolos-opos-spi, a dedicated QuteScriptEngineProvider implements ScriptEngineProvider:

package io.github.kriolos.opos.scripting.qute;

import com.openbravo.pos.spi.scripting.*;
import io.quarkus.qute.Engine;
import io.quarkus.qute.Template;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class QuteScriptEngineProvider implements ScriptEngineProvider {

    public static final String ENGINE_ID = "qute";
    private final Engine quteEngine = Engine.builder().addDefaults().build();
    private final Map<String, Template> cache = new ConcurrentHashMap<>();

    @Override
    public boolean hasEngine(String engineId) {
        return ENGINE_ID.equalsIgnoreCase(engineId);
    }

    @Override
    public String render(String engineId, String templateName, Map<String, Object> model) {
        Template template = cache.computeIfAbsent(templateName, quteEngine::getTemplate);
        var instance = template.instance();
        model.forEach(instance::data);
        return instance.render();
    }
}

8. 8. Scripting & Business Rules: BeanShell to QuickJS

8.1. 8.1 Architectural Motivation

User-configurable sales events, discount rules, and payment callbacks currently use BeanShell 2.x (bsh.Interpreter). BeanShell:

  • Is effectively unmaintained and stuck in Java 1.3 language syntax.

  • Has high memory overhead (~15MB overhead per complex interpreter session).

  • Relies on full dynamic JVM reflection, completely incompatible with GraalVM build-time analysis.

8.2. 8.2 Why QuickJS?

QuickJS (created by Fabrice Bellard) is an ultra-compact, high-performance embeddable JavaScript engine supporting the full ECMAScript 2020 specification:

  • Microscopic Footprint: Runtime engine size is under 300KB RAM with sub-millisecond execution startup.

  • Deterministic Sandboxing: Enforces strict instruction execution limits and memory ceilings, protecting POS terminals from infinite loops or memory leaks in user scripts.

  • Modern Developer Syntax: POS customizers write clean modern JavaScript (ES6+ arrow functions, const/let, destructuring, template literals) instead of dated Java 1.3 syntax.

  • Panama / FFM Ready: Embedded via lightweight JNI bindings or modern Java 22+ Foreign Function & Memory API (Project Panama), running with native execution speed.

8.3. 8.3 Implementation via ScriptEngineProvider SPI

package io.github.kriolos.opos.scripting.quickjs;

import com.openbravo.pos.spi.scripting.*;
import java.util.Map;

public class QuickJsScriptEngineProvider implements ScriptEngineProvider {

    public static final String ENGINE_ID = "quickjs";

    @Override
    public boolean hasEngine(String engineId) {
        return ENGINE_ID.equalsIgnoreCase(engineId) || "javascript".equalsIgnoreCase(engineId);
    }

    @Override
    public Object execute(String engineId, String script, Map<String, Object> bindings)
            throws ScriptEngineException {
        // Enforce execution sandbox: 50MB max memory, 2000ms max CPU time
        try (QuickJsContext ctx = QuickJsRuntime.createContext(50 * 1024 * 1024, 2000)) {
            bindings.forEach(ctx::bind);
            return ctx.evaluate(script);
        } catch (QuickJsTimeoutException e) {
            throw new ScriptEngineException("POS Script timed out after 2000ms execution limit", e);
        }
    }
}

10. 10. Reflection Registration Policy (Mandatory Rule)

Absolute Rule — No Configuration Properties for Reflection
Every class, field, method, or constructor that requires runtime or GraalVM native-image reflection registration MUST be declared programmatically in a single, canonical Java source file. Using reflect-config.json, resources-config.json, or any other JSON/YAML property configuration file for reflection registration is strictly prohibited in this project.

10.1. 10.1 Rationale

Reflection registrations scattered across multiple configuration files:

  • Fragment the contract — there is no single source of truth; changes require hunting across src/main/resources/META-INF/native-image/.

  • Are invisible to the compiler — typos in class names in JSON silently fail at native-image link time, not at build time.

  • Break refactoring — IDE rename/move refactorings do not update JSON entries, creating stale registrations that become dead weight or, worse, hidden security surface.

  • Oppose ArC build-time CDI — ArC already performs complete build-time analysis; adding JSON side-channels defeats the purpose.

10.2. 10.2 Canonical Registration Class

All reflection registrations live in one class per module:

package io.github.kriolos.opos.app.native_;

import io.quarkus.runtime.annotations.RegisterForReflection;

/**
 * SINGLE SOURCE OF TRUTH for all GraalVM native-image reflection registrations
 * in the kriolos-opos-app module.
 *
 * RULE: No reflect-config.json or resources-config.json files are allowed.
 *       Every reflection need MUST be declared here as code.
 *
 * HOW TO ADD A NEW ENTRY:
 *   1. Add the class to the @RegisterForReflection targets array below.
 *   2. Commit this file — code review enforces the single-place rule.
 */
@RegisterForReflection(
    targets = {
        // --- Receipt / Ticket model (used by Qute Engine API type-safe bindings) ---
        com.openbravo.data.loader.TableDef.class,
        com.openbravo.pos.ticket.TicketInfo.class,
        com.openbravo.pos.ticket.TicketLineInfo.class,
        com.openbravo.pos.ticket.TaxInfo.class,

        // --- Hardware SPI implementations discovered via ServiceLoader ---
        io.github.kriolos.opos.hardware.printer.EscPosReceiptPrinter.class,
        io.github.kriolos.opos.hardware.scale.NciScale.class,

        // --- FlatLaf / Look and Feel internals needed by Swing native rendering ---
        com.formdev.flatlaf.FlatLightLaf.class,
        com.formdev.flatlaf.FlatDarkLaf.class,

        // --- JasperReports compiled report classes (generated at build time) ---
        // Add each net.sf.jasperreports.engine.fill.JR* class explicitly here.
    },

Quarkus processes @RegisterForReflection at build time via the ArC annotation processor. The class is not instantiated at runtime; it is a pure metadata carrier.

10.4. 10.4 Code Review Gate

The following rule must be enforced in every Pull Request review checklist:

  • No reflect-config.json file was added or modified.

  • No resources-config.json file was added or modified.

  • Any new reflection need was added to the appropriate *ReflectionRegistrations.java class.

  • The targets array entry references a fully-qualified, import-resolvable class — not a string literal.

12. 12. Verification & Acceptance Criteria

  1. Cold Boot Benchmark: Cold start to visible Swing login screen under 1.5 seconds on standard hardware.

  2. Memory Footprint: Base memory footprint (resident set size) under 180MB at idle.

  3. Receipt Rendering Speed: Qute template render time under 2ms per receipt pass.

  4. Script Execution Safety: QuickJS terminates any customer script running longer than 2000ms with a graceful error.

  5. Thread Safety: All Swing mutations verified strictly executing on the Event Dispatch Thread via @RunOnEdt.

  6. Hardware Compatibility: Serial receipt printing, cash drawer kick, and barcode scan events function identically to legacy execution.

  7. Offline Resilience: Standalone SQLite database boots seamlessly without network or external services.

  8. Installer Validation: Standalone native installers (DEB, MSI, DMG) install cleanly without requiring an external Java Runtime Environment (JRE).

  9. Reflection Policy Compliance: Zero reflect-config.json or resources-config.json files present in the repository. All GraalVM reflection registrations are declared in the canonical *ReflectionRegistrations.java class of each module.
