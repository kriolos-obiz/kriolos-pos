= Modal Architecture Migration: Panel-First Design & PosUIModal
:navtitle: Modal Migration (PosUIModal)

This document specifies the architectural transition from legacy `javax.swing.JDialog` inheritance to a **Panel-First Modal Architecture** powered by `PosUIModal`.

== 1. Problem Statement & Motivation

Historically, modal interactions across KriolOS POS were implemented by having classes directly extend `javax.swing.JDialog`. This design created severe architectural and platform-level issues:

1. **Tight Container Coupling**: UI panels are permanently tied to a native top-level window. They cannot be hosted in-frame, embedded in tabs, rendered inside web wrappers, or tested without spawning native OS windows.
2. **Wayland & FlatLaf Black Buffer Rendering (BUG-001)**: On modern Linux Wayland compositors (Pop!_OS COSMIC / GNOME), unvalidated dialogs that omit explicit layout validation passes render with an unpainted, solid-black framebuffer until an external damage event (click/drag) is received.
3. **Modal Window Detachment & Focus Loss (BUG-002)**: On Linux XWayland, modal dialogs detach as secondary OS windows in the dock/taskbar. Clicking outside or focusing the main window causes the dialog to slip behind the main POS screen, leaving the UI unresponsive with the blocking dialog hidden.
4. **Fragmentation of Window Handling**: Over 20 dialogs independently attempt to resolve parent frames (`new JFrame()`, `SwingUtilities.windowForComponent`), frequently triggering `NullPointerException` when `parent == null`.

== 2. Architectural Solution: Panel-First Design (`PosUIModal`)

=== Core Principles
1. **Content Extends `javax.swing.JPanel`**: All dialog content forms extend `JPanel` rather than `JDialog`.
2. **Consistent Suffix Convention**: All modal panel classes must use the **`*ModalPanel`** suffix for clear categorization across the project.
3. **Centralized Modal Orchestration (`PosUIModal`)**: A unified, fluent controller in `com.openbravo.data.gui.modal.PosUIModal` handles presentation, window ownership, centering, and lifecycle.
4. **Pluggable Presentation Strategies**:
   * **`NATIVE_DIALOG`**: Managed `JDialog` wrapper with automatic owner resolution, FlatLaf framebuffer validation (curing `BUG-001`), and IntelliJ-style focus pinning (curing `BUG-002`).
   * **`IN_FRAME_OVERLAY`**: Single-window in-frame modal overlay rendered on `JRootFrame`'s `JLayeredPane.MODAL_LAYER` with a darkened backdrop scrim and `SecondaryLoop` blocking—**completely eliminating secondary OS windows**.
   * **Configurable**: Configurable at runtime via `ui.modal.mode = dialog | overlay` or `-Dkriolos.ui.modal.mode=...`.

== 3. NetBeans GUI Builder (`.form`) Specification

When converting dialogs designed with the NetBeans GUI Builder:

[IMPORTANT]
====
NetBeans `.form` files are XML metadata paired with Swing classes.
* For `JDialog`, the root element is:
  `+<Form type="org.netbeans.modules.form.forminfo.JDialogFormInfo">+`
* For `JPanel`, the root element MUST be:
  `+<Form type="org.netbeans.modules.form.forminfo.JPanelFormInfo">+`

If a `.java` file is changed to `extends JPanel` without updating `.form`, NetBeans GUI Builder will regenerate incompatible `JDialog` methods (`setDefaultCloseOperation`, `pack()`) inside `//GEN-BEGIN:initComponents`, breaking compilation.
====

=== Backward-Compatible Migration Pattern
To guarantee zero regressions and seamless backwards compatibility:
1. Create the new visual form as `*ModalPanel.java` + `*ModalPanel.form` with `JPanelFormInfo`.
2. Keep the legacy `*Dialog.java` as a thin delegate wrapper:
[source,java]
----
public class JEditorTextDialog extends JDialog {
    public static String showEditor(Component parent, String title) {
        EditorTextModalPanel panel = new EditorTextModalPanel();
        PosUIModal modal = PosUIModal.create(parent, panel).setTitle(title);
        modal.show();
        return panel.getValue();
    }
}
----

== 5. BeanShell Script Templates (`.bs`) Audit (Read-Only)

[IMPORTANT]
====
**CRITICAL PROJECT RULE**:
BeanShell (`.bs`) template files **MUST NOT BE MODIFIED** during this migration. They are audited and formally documented below for reference and future roadmap enhancements only.
====

Multiple dynamic BeanShell script templates located in `kriolos-opos-app/src/main/resources/com/openbravo/pos/templates/` currently invoke dialogs directly, typically passing `null` as the parent window:

=== Future Roadmap for Scripting (Deferred)
When BeanShell modernization is prioritized in a future milestone:
1. Expose `PosUIModal` into the BeanShell scripting context (e.g., as a global `modal` helper or static utility).
2. Scripts will then be updated to call `modal.showMessage(...)`, `modal.confirm(...)`, or `modal.input(...)` so they automatically bind to `JRootFrame` and participate in the in-frame modal overlay or focus guard without spawning unparented OS windows.
3. For now, all `.bs` files remain strictly untouched.
