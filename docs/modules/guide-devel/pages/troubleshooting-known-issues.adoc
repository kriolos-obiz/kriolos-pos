== [BUG-001] Dialog Opens with Black Content on Pop!_OS 24.04 LTS

[cols="1,3"]
|===
| **Issue ID** | BUG-001
| **Status** | Queued for Resolution
| **Reported Platform** | Linux Pop!_OS 24.04 LTS (Noble), COSMIC / Wayland
| **Component** | Swing Dialogs (`JMessageDialog`, `JOptionPane`, FlatLaf)
|===

=== Symptom
When opening modal dialogs (such as database error notifications or message dialogs), the window contents appear completely black/blank upon initialization. The UI components (labels, buttons, text areas) only render after the user clicks inside the dialog or moves/drags the window across the screen to force a repaint event.

=== Technical Root Cause
In `JMessageDialog.java`, the dialog sets a hardcoded size (`setSize(new Dimension(482, 345))`) inside `initComponents()`, but **never invokes `pack()`**, **never calls `setLocationRelativeTo(...)`**, and **never invokes `revalidate()` / `repaint()`** prior to `setVisible(true)`. On modern Linux XWayland/Wayland compositors with FlatLaf dark themes, showing an unvalidated window leaves the backing buffer unpainted until an external damage event (click/drag) is issued.

=== Resolution Plan
1. Call `myMsg.pack()` to calculate dynamic component layout geometry.
2. Call `myMsg.setLocationRelativeTo(owner)` to center the dialog over its parent.
3. Call `myMsg.revalidate()` and trigger an explicit repaint pass prior to mapping.

== [BUG-002] Modal Dialog Detaches as 2nd Window and Disappears Behind Main Window

[cols="1,3"]
|===
| **Issue ID** | BUG-002
| **Status** | Queued for Resolution
| **Reported Platform** | Linux Pop!_OS 24.04 LTS (Noble), COSMIC / Wayland / X11
| **Component** | `JMessageDialog`, `JDialog` window ownership & modality
|===

=== Symptom
1. When a modal blocking dialog opens, it creates a second, detached window in the OS taskbar/dock and Alt+Tab switcher.
2. Clicking outside the dialog or clicking the main application window causes the dialog to disappear behind the main window.
3. Users lose visibility of the blocking dialog while the main window remains unresponsive.

=== Comparison of IDE Behaviors
* **NetBeans IDE Behavior**: Opens dialog as a 2nd window; clicking main window brings main window forward *without* the dialog, burying it behind.
* **IntelliJ IDEA Behavior**: Opens dialog as a 2nd window; clicking main window immediately brings the main window *with the modal dialog pinned on top and blocked*. The dialog never gets lost.
* **Target POS Behavior**: At minimum IntelliJ IDEA behavior (pinned on top, never hidden); ideal target is a single-window in-frame overlay.

=== Technical Root Cause
In `com.openbravo.data.gui.JMessageDialog.java` (lines 50–58):
[source,java]
----
private static Window getWindow(Component parent) {
    if (parent == null) {
        return new JFrame(); // <--- CRITICAL BUG!
    } else if (parent instanceof Frame || parent instanceof Dialog) {
        return (Window) parent;
    } else {
        return getWindow(parent.getParent());
    }
}
----
When `parent` is null or not yet attached to a Frame, `getWindow` constructs a disposable `new JFrame()`. Because the dialog's owner is a dummy invisible frame rather than the real `JRootFrame`, the Linux window manager receives no `WM_TRANSIENT_FOR` relationship. The dialog becomes an independent root window that detaches from the main window and drops behind it upon focus change.

=== Resolution Strategies (Queued for Next Sprint/Issue)

==== Strategy A: Solid Window Ownership & Focus Guard (IntelliJ Pattern)
1. **Real Ancestor Resolution**: Replace `new JFrame()` with active `JRootFrame` detection:
[source,java]
----
private static Window getWindow(Component parent) {
    if (parent != null) {
        Window w = SwingUtilities.getWindowAncestor(parent);
        if (w != null) return w;
    }
    for (Frame f : Frame.getFrames()) {
        if (f.isShowing() && f instanceof JRootFrame) return f;
    }
    return JOptionPane.getRootFrame();
}
----
2. **Window Focus Guard**: Add a `WindowFocusListener` to the owner window while the dialog is active. When the main window receives focus or is clicked, it immediately calls `dialog.toFront()` and `dialog.requestFocus()`, ensuring the dialog never goes behind.

==== Strategy B: Single-Window In-Frame Modal Overlay
Render modal dialogs directly inside `JRootFrame`'s `GlassPane` or `JLayeredPane.MODAL_LAYER`:
* **Zero OS Windows**: Exactly 1 window in the OS taskbar and dock.
* **Dimmed Backdrop**: Semi-transparent dark overlay blocking clicks to background POS panels.
* **Wayland Immune**: Completely bypasses all XWayland window mapping and multi-window compositor bugs.
